# گزارش تحویل نسخهٔ 2.4.1 — سبک‌سازی پویش کل بازار

تاریخ: ۲۰۲۶-۰۹-۲۴ · نسخهٔ قبلی: 2.4.0 · وضعیت گیت: **بدون commit/push** (2.4.0 و 2.4.1)

## گزارش کاربر

> «بخش سیگنال خیلی خوب شد، ولی سیستم خیلی سنگین شده، هنگ می‌کند و کار جلو نمی‌رود.
> نرم‌افزار کرش می‌کند و کل سیستم را درگیر خودش می‌کند.»

## علت‌ها (اندازه‌گیری‌شده، نه حدسی)

همهٔ کارهای ناهمگام برنامه — وب‌سوکت، داشبورد، معاملهٔ خودکار و پویش — روی **یک**
حلقهٔ asyncio در یک نخ اجرا می‌شوند. پویش کل صرافی (۱۰۰۰+ نماد × ۴ تایم‌فریم ≈ ۴۰۰۰
درخواست کندل) پنج گلوگاه را هم‌زمان فعال می‌کرد:

1. **نوشتن هر کندل در پایگاه داده.** هر پاسخ کندل (۳۰۰ کندل) با ORM در SQLite ذخیره
   می‌شد: برای کل صرافی حدود ۱٫۲ میلیون ردیف در هر پویش، با commit جدا برای هر
   درخواست. اندازه‌گیری: ~۱۲ms CPU برای هر ذخیره به‌علاوهٔ نوشتن روی دیسک. همین
   «درگیرشدن کل سیستم» (دیسک مشغول، پایگاه دادهٔ رو به رشد) را می‌ساخت.
2. **پرشدن حافظهٔ نهان مشترک.** کندل‌های پویش ظرفیت ۵۰۰تایی کش را پر می‌کردند و چون
   حذف بر پایهٔ «نزدیک‌ترین انقضا» است، تیکر و قیمت‌های داغ داشبورد و معاملهٔ خودکار
   بیرون می‌افتادند → درخواست REST اضافه → محدودیت نرخ صرافی.
3. **قفل‌شدن حلقهٔ شبکه.** محاسبهٔ اندیکاتورها هم‌گام است؛ در پویش موازی تا ۱۶ محاسبه
   پشت‌سرهم اجرا می‌شد. اندازه‌گیری: تأخیر تایمرهای حلقه تا **۴۰۶ms** و مصرف CPU
   **۸۹–۹۹٪**. در این مدت پینگ وب‌سوکت و معاملهٔ خودکار جا می‌ماندند و نخ رابط
   کاربری (که با GIL پایتون رقابت می‌کند) کند/بی‌پاسخ می‌شد.
4. **ساخت تکراری DataFrame.** با پروفایل مشخص شد هر اندیکاتور کندل‌ها را جداگانه به
   DataFrame تبدیل می‌کرد (کامنت کد می‌گفت «یک بار»، ولی پیاده‌سازی این کار را نمی‌کرد):
   **~۳۵٪** CPU هر نماد.
5. **جدول پویش سنگین.** با پویش زنده، جدول هر ۸۰۰ms با همهٔ ردیف‌ها (هر ردیف یک
   دکمهٔ واقعی) از نو پر می‌شد و ستون‌های «به اندازهٔ محتوا» با هر خانه همهٔ ردیف‌ها را
   دوباره اندازه می‌گرفتند؛ گزارش پیشرفت هم برای هر نماد یک رویداد رابط می‌ساخت.

## اصلاحات

| بخش | تغییر |
| --- | --- |
| `market/engine.py` | `bulk_fetch()` (ContextVar): درخواست‌های کندلِ پویش نه در پایگاه داده نوشته می‌شوند نه در کش مشترک می‌نشینند. فقط کارهای همان پویش را تحت تأثیر قرار می‌دهد؛ نمودار، داشبورد و معامله مثل قبل کش و ذخیره دارند. |
| `signals/scanner.py` | `CpuGovernor`: سقف سهم CPU نخ شبکه — پویش دستی **۶۰٪** و خودکار **۳۵٪** یک هسته. پس از هر نماد اگر از سهم جلو زده باشد، کوتاه مکث می‌کند. در مکث محدودیت نرخ صرافی، پویش صبر می‌کند (قبلاً صدها نماد فوراً «شکست» می‌خوردند و سراغ کندل ذخیره‌شده در دیسک می‌رفتند). |
| `signals/engine.py` | «دروازهٔ محاسبه»: هر بار فقط یک محاسبهٔ سنگین روی حلقه و بین دو محاسبه نوبت به وب‌سوکت و تایمرها داده می‌شود. |
| `indicators/engine.py`، `indicators/base.py` | یک DataFrame برای همهٔ اندیکاتورهای یک تایم‌فریم؛ تبدیل NaN با numpy. خروجی دقیقاً همان است (آزمون مقایسه‌ای). |
| `app/application.py` | ذخیرهٔ سیگنال‌های پویش هر ۲۰ مورد یک بار حلقه را آزاد می‌کند. |
| صفحهٔ سیگنال | جدول حداکثر **۲۰۰** سیگنال برتر (پیام «بهترین ۲۰۰ از N»)، رسم یک‌جا بدون اندازه‌گیری میانی. |
| کنترلر | گزارش پیشرفت دستی حداکثر ~۷ بار در ثانیه و خودکار ۲ بار در ثانیه؛ تازه‌سازی زندهٔ جدول تطبیقی (۰٫۸ تا ۵ ثانیه، حداکثر ~۱۰٪ وقت رابط). پویش خودکار با سهم CPU پس‌زمینه. |

## نتیجهٔ اندازه‌گیری (همین sandbox، دادهٔ ساختگی، ۸۰ نماد × ۴ تایم‌فریم)

| معیار | 2.4.0 | 2.4.1 |
| --- | --- | --- |
| CPU هر نماد (۴ تایم‌فریم) | ۹۰ms | ۴۷ms |
| تأخیر بیشینهٔ حلقهٔ شبکه | ۴۰۶ms | ۳۶–۴۵ms |
| مصرف CPU نخ شبکه در پویش دستی | ۸۹٪ | ۶۲٪ (سقف ۶۰٪) |
| مصرف CPU در پویش خودکار | ۸۹٪ | ۳۷٪ (سقف ۳۵٪) |
| نوشتن کندل در پایگاه داده در هر پویش کل صرافی | ~۱٫۲ میلیون ردیف | ۰ |

روی ویندوز و سخت‌افزار شما عددهای مطلق فرق می‌کنند؛ نسبت‌ها باید مشابه باشند. پویش
کل صرافی به‌خاطر سقف CPU کمی طولانی‌تر می‌شود، ولی برنامه و سیستم روان می‌مانند.

## پیشنهاد استفاده

- اگر سیستم ضعیف است: «پالایش هوشمند» روشن و «کمینهٔ گردش ۲۴ساعته» مثلاً ۵۰۰K$ —
  صدها بازار بی‌معامله کنار می‌روند و پویش چند برابر کوتاه‌تر می‌شود.
- کندل‌هایی که پویش‌های 2.4.0 در پایگاه داده نوشته‌اند سر جایشان می‌مانند (این نسخه
  داده‌ای حذف نمی‌کند)؛ فقط دیگر چیزی اضافه نمی‌شود.
