## ۱) داده زندهٔ صرافی‌ها

### اشکالی که رفع شد

موتور بازار به‌صورت ثابت `LBankWebSocketClient` می‌ساخت. توبیت هم
`supports_websocket=True` اعلام می‌کرد ولی هیچ کلاینتی نداشت. نتیجه:
کاربری که توبیت را انتخاب می‌کرد، **داده زندهٔ LBank** می‌گرفت — قیمت
صرافی دیگری روی صفحه می‌نشست.

### معماری تازه

هر صرافی کلاینت خودش را می‌سازد:

```
ExchangeProvider.create_websocket_client()  →  MarketWebSocketClient
```

`MarketWebSocketClient` یک `Protocol` در `market/providers/base.py` است.
موتور فقط با همین امضاها کار می‌کند و دیگر نام هیچ صرافی‌ای را نمی‌داند:

| متد | کار |
|---|---|
| `start()` / `stop()` | چرخهٔ عمر |
| `subscribe_ticker(symbol)` | اشتراک قیمت لحظه‌ای |
| `subscribe_candles(symbol, tf)` | اشتراک کندل زنده |
| `unsubscribe_all()` | پاک‌سازی هنگام تعویض نماد |
| `status` | وضعیت اتصال |

پیاده‌سازی پیش‌فرض `create_websocket_client()` مقدار `None` برمی‌گرداند
یعنی «داده زنده ندارم» و موتور به نظرسنجی REST بسنده می‌کند. اگر صرافی
`supports_websocket=True` بدهد ولی کلاینت ندهد، موتور **هشدار می‌دهد و
به REST برمی‌گردد** — دیگر بی‌صدا به صرافی اشتباه وصل نمی‌شود.

### پروتکل توبیت

نشانی: `wss://stream.toobit.com/quote/ws/v1`

</div>

```jsonc
// اشتراک
{"symbol":"BTCUSDT","topic":"realtimes","event":"sub","params":{"binary":false}}
{"symbol":"BTCUSDT","topic":"kline_1m","event":"sub","params":{"binary":false}}

// لغو اشتراک — رویداد «cancel» است نه «unsub»
{"symbol":"BTCUSDT","topic":"realtimes","event":"cancel","params":{"binary":false}}
```

<div dir="rtl">

نکته‌هایی که با اتصال واقعی راستی‌آزمایی شد:

۱. **پاسخ کندل `topic` را `kline` می‌دهد، نه `kline_1m`.** نوع بازه جدا
   می‌آید و گاهی **فقط داخل `params`** است؛ هر دو جا خوانده می‌شود.
۲. **درصد تغییر در فیلد `m` کسری است** (‎`-0.0009`‎ یعنی ‎-۰٫۰۹٪‎) و باید
   در ۱۰۰ ضرب شود. بدون این، ستون «تغییر» صدبرابر کوچک نشان داده می‌شد.
۳. **زمان کندل میلی‌ثانیه است** و مدل داخلی ثانیه می‌خواهد.
۴. **سرور توبیت ping نمی‌فرستد** (برخلاف LBank). در آزمون ۷۵ ثانیه‌ای
   هیچ فریم ping نیامد، پس زنده‌نگه‌داشتن اتصال بر عهدهٔ خود کلاینت است
   (`ping_interval=20`). با این حال اگر روزی سرور ping بفرستد، کلاینت
   `pong` می‌دهد — بیمهٔ ارزانی در برابر یک قطعی مرموز.
۵. نماد نامعتبر پاسخ `{"code":"-100010","desc":"Invalid Symbols!"}` دارد
   که فقط لاگ می‌شود و اتصال را نمی‌شکند.

### افزودن وب‌سوکت به صرافی تازه

</div>

```python
def create_websocket_client(self, *, on_ticker=None, on_candle=None,
                            on_status_change=None):
    """درون‌ریزی تنبل تا نصب‌های بدون داده زنده هم بالا بیایند."""
    from market.providers.myexchange.websocket_client import MyWebSocketClient

    return MyWebSocketClient(
        on_ticker=on_ticker,
        on_candle=on_candle,
        on_status_change=on_status_change,
    )
```

## ۲) پاسخ جریانی چت

### چه چیزی عوض شد

پیش از این، کاربر تا آمادن‌شدن **کل** پاسخ فقط «در حال فکر کردن…»
می‌دید. حالا متن مثل تایپ‌شدن، تکه‌تکه ظاهر می‌شود.

### مسیر داده

</div>

```
سرویس هوش مصنوعی  ──SSE──▶  OpenAICompatibleProvider.stream()
                                      │ تکهٔ خام
                                      ▼
                            AIProviderManager.stream()   ← زنجیرهٔ جایگزینی
                                      │
                                      ▼
                        StreamingAnswerExtractor.feed()  ← فقط «answer»
                                      │ دلتای قابل نمایش
                                      ▼
                     MainController.chat_stream_delta (Signal)
                                      │ عبور امن از نخ
                                      ▼
                            ChatPage.stream_delta()
```

### چرا استخراج‌گر لازم است

عامل گفتگو از مدل می‌خواهد پاسخ را در قالب JSON بدهد:

```json
{"answer": "سلام ...", "action": {...}}
```

در حالت جریانی، متن تکه‌تکه می‌رسد و تا لحظهٔ آخر JSON **ناقص** است. اگر
تکه‌های خام را مستقیم نمایش دهیم، کاربر چیزی مثل `{"answer": "سلا`
می‌بیند. `StreamingAnswerExtractor` مقدار `answer` را در حال شکل‌گیری
بیرون می‌کشد و فقط **دلتا** را برمی‌گرداند.

توانایی‌هایش:

- JSON ناقص و شکسته در هر نقطه (حتی وسط نام کلید)
- گریزهای `\n`، `\t`، `\"` و `\uXXXX` — حتی وقتی گریز یونیکد **بین دو
  تکه** نصف شده باشد
- حصار ```` ```json ````
- متن ساده (اگر مدل اصلاً JSON ندهد)
- کلید جایگزین `text`

**درخواست ابزار خودبه‌خود نامرئی می‌ماند:** چون استخراج‌گر فقط `answer`
را می‌خواند، خروجی `{"tool": ...}` چیزی روی صفحه نمی‌گذارد و کاربر فقط
«در حال گرفتن قیمت…» را می‌بیند.

> **درسی که از آزمون زنده گرفتیم:** نسخهٔ اول، جریان را در دور اول خاموش
> می‌کرد تا درخواست ابزار پخش نشود. همهٔ آزمون‌های واحد سبز بودند، ولی در
> برنامهٔ واقعی ابزارها **همیشه** ثبت‌اند و رایج‌ترین حالت (پرسش ساده)
> در همان دور اول پاسخ می‌گیرد — پس عملاً هیچ‌وقت جریانی در کار نبود.
> حالا همهٔ دورها جریانی‌اند و پنهان‌ماندن درخواست ابزار را استخراج‌گر
> تضمین می‌کند. آزمون
> `test_agent_streams_even_when_tools_are_registered` همین را می‌پاید.

### ایمنی نخ

تکه‌ها از **نخ شبکه** می‌آیند ولی ویجت فقط در **نخ رابط کاربری** قابل
تغییر است؛ دست‌زدن به ویجت از نخ دیگر برنامه را می‌کشد. برای همین
`MainController` یک سیگنال Qt دارد:

</div>

```python
chat_stream_delta = Signal(str, bool)   # (دلتا، جایگزین‌شود؟)
```

Qt تحویل امن به نخ درست را خودش انجام می‌دهد.

### بازگشت خودکار

جریان هیچ‌وقت باعث خطا برای کاربر نمی‌شود:

| حالت | رفتار |
|---|---|
| سرویس `stream` ندارد | پیاده‌سازی پیش‌فرض `generate()` را صدا می‌زند و کل متن را یک تکه می‌دهد |
| جریان شکست شبکه‌ای خورد | خودکار `generate()` معمولی |
| جریان هیچ متنی نداد | خودکار `generate()` معمولی |
| سرویس وسط راه مرد | متن نیمه‌کاره پاک و سرویس بعدیِ زنجیره امتحان می‌شود |

قرارداد پاک‌سازی ساده است: **دلتای خالی یعنی «هرچه نشان داده‌ای را دور
بریز»**. مصرف‌کننده‌ای که این را نفهمد هم آسیبی نمی‌بیند، چون افزودن
رشتهٔ خالی بی‌اثر است.

### تنظیمات

«تنظیمات ← کارایی ← نمایش تدریجی پاسخ» (کلید `ai.chat_streaming`).
پیش‌فرض **روشن** است؛ چون همهٔ مسیرهای شکست بازگشت خودکار دارند،
روشن‌بودنش بی‌خطر است. این کلید جزو ترجیحات کاربر است و با حساب او
ذخیره می‌شود.
